## Why Qarar?

Hardcoded `if/else` chains tie business rule updates to software release cycles. A routine change to discount tiers, fraud score thresholds, or access policies requires a code commit, pull request review, and server redeployment.

Qarar treats business rules as portable, technology-agnostic JSON trees. Store rules in PostgreSQL, MongoDB, or Redis, and evaluate them dynamically at runtime:

- **No deployments for logic changes**: Update rule definitions in your database or admin UI; production services apply them immediately.
- **Run in-memory or in database**: Check incoming payloads in Node.js or push the rule down into a SQL `WHERE` clause or MongoDB query filter.
- **Built-in explanations**: When a rule evaluation fails, Qarar returns the exact condition that failed in plain language for audit logs and customer support.

---

## How It Works

Define a rule using the fluent builder (or load pre-stored JSON AST from your database), evaluate against input data, and receive a boolean verdict with failure triage:

```ts
import { checkRule, rule } from "@qarar/sdk";

// 1. Define rule (or load JSON AST from your database)
const loyaltyDiscount = rule("Loyalty Checkout Discount")
  .where("user.tier").in(["gold", "vip"])
  .and("cart.total").gte(100)
  .build();

// 2. Evaluate incoming payload
const { result, reasons } = checkRule(loyaltyDiscount, {
  user: { tier: "bronze" },
  cart: { total: 150 }
});

console.log(result);  // false
console.log(reasons); // ['user.tier: "bronze" is not in [gold, vip]']
```

## Capabilities

<CardGrid>
  <Card title="Zero-Deploy Logic">
    Store rules as standard JSON in PostgreSQL, MongoDB, or Redis. Update business logic live without rebuilding or redeploying code.
  </Card>
  <Card title="Database Pushdown">
    Compile the same rule AST into parameterized SQL `WHERE` clauses or MongoDB filter objects to filter data directly in the database.
  </Card>
  <Card title="Audit Explanations">
    Generate human-readable failure explanations automatically. Know exactly why an order was flagged or a user was denied without log grepping.

    Safe evaluation with zero `eval()` and guarded field lookups that prevent prototype pollution. Guaranteed deterministic termination.
